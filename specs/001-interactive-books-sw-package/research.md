# Phase 0 Research: Interactive Books Service Worker Package Integration

## 1. How does `sw-src.js` gain access to npm packages?

**Decision** *(confirmed against the actual published package — its README documents this exact mechanism)*: Convert `sw-src.js` → `sw-src.ts` and build it via **`workbox-webpack-plugin`'s `InjectManifest` plugin**, added to the existing `webpack.config.js` alongside `HtmlWebpackPlugin`, configured through the package's own `createInjectManifestOptions()` helper. `InjectManifest` runs `swSrc` through webpack's own compiler (a child compilation reusing the parent config's `module.rules`, i.e. `ts-loader`), so `sw-src.ts` can `import` from `@curiouslearning/sw` and `workbox-*` npm packages exactly like `App.ts` can. This replaces the separate `npx workbox injectManifest` CLI step (and `workbox-config.js`) — `sw.js` becomes an output of the single `webpack` build.

**Rationale**: Today `sw-src.js` is never touched by webpack/ts-loader — it loads Workbox from a CDN via `importScripts("https://storage.googleapis.com/workbox-cdn/...")`, and `workbox-cli`'s `injectManifest` (driven by `workbox-config.js`) only performs a text substitution of `self.__WB_MANIFEST` on that raw file; it does not bundle or resolve npm imports. `@curiouslearning/sw` ships as ESM/CJS npm modules (`dist/sw.mjs`/`dist/sw.cjs`), not a CDN script, so it can only be consumed via a bundler. The package's own README shows `createInjectManifestOptions()` being passed straight into `new InjectManifest(...)` from `workbox-webpack-plugin` — that plugin (not `workbox-cli`) is the intended, documented integration point, and it is the standard Workbox-recommended pattern for a service worker source that needs npm imports. This also mirrors the shape of change on the sibling Assessments PR (#296 in `assessment-survey-js`), which touched `webpack.config.js`, added `sw-src.ts`, and touched `workbox-config.js` (there, likely reduced to nothing / removed).

**Alternatives considered**:
- *Add `sw-src.ts` as a plain second webpack `entry` and keep running `workbox-cli injectManifest` against its built output* (the original plan-time guess, made before the package's README was reachable): works mechanically, but duplicates a build step the package's own `createInjectManifestOptions()` helper is explicitly designed to make unnecessary, and leaves two separate manifest-injection code paths (webpack's asset pipeline vs. a standalone CLI invocation) to keep in sync. Rejected once the real README confirmed the plugin-based path is what the package expects.
- *Keep `importScripts` and vendor a UMD build of the package onto a CDN/self-hosted URL*: rejected — the package isn't published as a UMD/CDN bundle (only `.cjs`/`.mjs`/`.d.ts` entries), and hand-rolling a CDN build would duplicate exactly the maintenance burden the shared package exists to eliminate.
- *Pull in only the specific runtime functions via a lightweight hand-copy*: rejected — defeats FR-006 (must use the shared, centrally-maintained package, not a local reimplementation) and the parent epic's stated goal (MR-167).

## 2. Workbox major-version upgrade (6.5.4 → 7.4.1)

**Decision**: Bump `workbox-core`, `workbox-precaching`, `workbox-routing`, `workbox-strategies`, `workbox-expiration`, `workbox-window`, and `workbox-cli` to `^7.4.1` in `package.json`, and drop the CDN `importScripts` of `workbox-sw.js@6.2.0` in favor of importing `precacheAndRoute` from `workbox-precaching` directly inside the now-bundled `sw-src`.

**Rationale**: `@curiouslearning/sw`'s peer dependencies pin `workbox-core`/`workbox-precaching`/`workbox-routing` to `^7.4.1`; npm peer-dependency resolution requires the app's own Workbox packages to satisfy that range too, and running two major versions of Workbox side by side (CDN 6.x for precaching, npm 7.x for the shared package) in the same worker is unsupported and untested. This also brings this app in line with FTM/Assessments, which is the whole point of the shared package (consistent behavior, per MR-171's cross-app verification goal).

**Alternatives considered**: Stay on Workbox 6 and skip the parts of `@curiouslearning/sw` that need `workbox-precaching`/`workbox-routing` (i.e. only take `registerServiceWorkerUpdates`/`registerUpdateNotifier`, which don't appear to need those peers directly) — rejected as fragile: peer-dependency ranges are declared at the package level, not per-export, so npm/webpack tooling would still flag or refuse to resolve them cleanly, and it would leave this app on an unsupported Workbox version going forward.

## 3. Avoiding a message-protocol collision on `BroadcastChannel("cr-message-channel")`

**Decision**: Let `@curiouslearning/sw`'s `registerServiceWorkerUpdates()` / `registerUpdateNotifier()` use their own default channel (`DEFAULT_CHANNEL_NAME` — confirmed from the package's type declarations to be `'sw-update-channel'`, distinct from this app's channel; configurable via the `channelName` option) for the generic update-lifecycle handshake, **separate from** this app's existing `"cr-message-channel"`, which keeps carrying only this app's own `Cache` (book-specific caching request) / `CachingProgress` messages exactly as today. Do not attempt to multiplex the package's lifecycle messages onto the existing channel. Use `mode: 'confirm'` (the package's default) on `registerServiceWorkerUpdates()` — its README states this mode "matches both FTM's and assessment-survey-js's current UX", i.e. a blocking `confirm()` dialog + reload on accept, which is exactly this app's current `handleUpdateFoundMessage()` behavior, so no `onUpdateAvailable`/`'custom'` callback is needed to preserve FR-002.

**Rationale**: The package's message vocabulary (`SwMessageType = 'Cache' | 'CacheUpdate' | 'Loading' | 'UpdateReady'`) is a generic, cross-app protocol — its `'Cache'` type is not guaranteed to mean the same thing as this app's existing `command: "Cache"` payload (`{ bookData, contentFile, lang }`, meaning "please download and cache this specific book's assets"). Reusing one channel for both would risk `App.ts`'s existing `onmessage` handler misinterpreting a package-originated message (or vice versa) purely because the `command`/type string happens to collide. Both registration functions accept an explicit `channelName`, so keeping them on separate channels is a supported, low-risk configuration rather than a workaround.

**Alternatives considered**: Reuse `"cr-message-channel"` for everything and rename this app's own `Cache`/`CachingProgress` commands to avoid the collision — rejected as higher-risk and higher-effort: it would touch every consumer of those message names (`App.ts`, `sw-src.js`, `GdlBookRuntime.ts` caching trigger) purely to make room for a protocol this app doesn't otherwise need to share, versus just pointing the package at its own channel name.

## 4. Where does `cacheUrlsWithProgress()` fit into the existing CR/GDL caching code?

**Decision**: Replace the hand-rolled batch loop inside `cacheBookAssets()` (open cache → chunk into batches of 5 → `cache.add()` per file with per-file fallback → `postMessage` progress after each batch → 100ms delay) with a call to `cacheUrlsWithProgress(cache, urls, { onProgress, onItemError })`, keeping `onProgress` post the same `{ command: "CachingProgress", data: { progress, bookName } }` shape on `"cr-message-channel"` that `App.ts` already expects, and `onItemError` preserving the existing "best-effort, skip missing assets, keep going" behavior. `cacheTheBookJSONAndImages()` and `cacheGdlBookAssets()` keep their app-specific URL-list-building logic (H5P page/element walk vs. GDL `content.json` walk) unchanged — only the generic "cache this list of URLs with progress" tail end is swapped.

**Rationale**: `cacheUrlsWithProgress(cache, urls, options)`'s shape (`Cache` + `string[]` + progress/error callbacks) is close to a drop-in replacement for the existing loop's inputs/outputs, satisfying FR-006 (use the shared package) without touching the two book-type-specific URL-collection code paths that have no equivalent in the shared package (and are explicitly out of scope for the parent epic to generalize).

**Alternatives considered**: Leave `cacheBookAssets()` untouched and only adopt the update-lifecycle pieces of the package — rejected as inconsistent with the epic's intent to reduce duplicated SW logic across sub-apps wherever the shared package already covers it, and it would leave this app's batching/progress semantics silently diverging from the package's (already-reviewed) implementation over time.

## 5. Verification approach (no test suite in repo)

**Decision**: Manual verification via `quickstart.md`, run locally with `npm run dev` (webpack build + `injectManifest` + `live-server`) and Chrome DevTools (Application → Service Workers / Cache Storage, Network → Offline throttling), covering: (a) first-load caching + progress milestones, (b) offline reload of an already-cached book (CR and GDL), (c) simulated update (bump `workbox-config.js`-driven precache revision, or a content file, then reload) confirming the "update available" prompt appears only after the new worker has taken control and that accepting it serves the new content.

**Rationale**: `CLAUDE.md` is explicit that this repo has no test suite, linter, or reliable `tsc --noEmit` signal — `webpack` build success plus manual DevTools verification is the established correctness bar here. Introducing a test framework is out of scope for this feature (not requested by the ticket, would expand scope well beyond the epic's stated boundaries).

**Alternatives considered**: Add an automated test harness (e.g. Playwright driving offline/online transitions) as part of this change — rejected as out of scope; MR-171 ("Verify and validate update behavior across all sub-apps") is a separate ticket in the same epic explicitly scoped to cross-app manual/automated verification, so introducing tooling here would duplicate or preempt that work.
